## 1. Bottom line

1. **dgem is more accurate on general decisions. The two are level on tasks Strands was trained on.**
   - JevBench public (231 items, 3 runs): dgem 194 / 194 / 195, Strands 169 / 169 / 169 (McNemar p = 3.5e-4). On the
     hard tier (111 items) dgem scores 67% and Strands 50%.
   - On items from datasets in Strands' training mix (n = 142): Strands 85.9%, dgem 85.2%.
   - On items with no known relation to its training data (n = 2,346): dgem 72.5%, Strands 62.7%.
   - Frozen sets (one scored run each): MASSIVE (51 languages) dgem 82.8% vs 67.2%; XNLI dgem 70.0% vs 63.7%;
     typed-decisions dgem 71.8% vs 60.2%.
2. **The comparison found a dgem defect.**
   - Two yes/no questions in one request whose correct answers have opposite polarity tend to get the same answer.
   - On a 51-case tool-call gate built from Strands' own agent example, dgem's two answers matched in 34–40 cases (gold: 7) and it scored 58%, against 86% for Strands.
   - Asked one question per request, dgem scores 100 of 102.
   - Now [`PROP-19`](/dgem/experiments/proposed/#prop-19-cross-slot-coupling-on-mixed-polarity-yesno-questions) and the matrix v2 suite `gate_mixed_noul`.
3. **Calibration: Strands is cautious, dgem is sharp but overconfident off its development suites.**
   - On JevBench, Strands has the lower ECE (0.048 vs 0.071). dgem has the lower Brier score (0.224 vs 0.348) and the higher AUROC (0.877 vs 0.806).
   - With one held-out temperature (T ≈ 1.5), dgem's pooled ECE falls from 0.069 to 0.028. Strands' falls from 0.037 to 0.031.
   - Out of domain, Strands rarely reaches 0.9 confidence (XNLI 0.1% of answers), while raw dgem is 74% correct at ≥ 0.9 on XNLI. See [`PROP-20`](/dgem/experiments/proposed/#prop-20-shipped-temperature-per-question-type-and-domain).
4. **Latency: Strands is faster on short inputs, dgem on long inputs, many questions and under load.**
   - Server p50 for one question over about 200 tokens: Strands 34 ms, dgem 54 ms.
   - Over about 3,800 tokens: Strands 118 ms, dgem 62 ms. The crossover is about 1,700 tokens.
   - Peak throughput with 5 questions per request: dgem 321 decisions/s, Strands 66.
5. **Determinism and cold start favour Strands.**
   - Strands returned identical probabilities on all 1,509 repeated requests. dgem changed 6.4% of answers.
   - Strands cold-starts in 38 s on Cloud Run.
6. **Strands' own numbers reproduce.**
   - The official JevBench harness at the commit Strands pinned matches its published per-task predictions on 229 of 231 tasks (169 correct vs 167 published).

## 2. What we compared

| | Strands Decider 2B v19 | dgem |
|---|---|---|
| Model | Qwen3.5-2B torso (1.9B dense), LM head removed | DiffusionGemma 26B-A4B MoE (3.8B active), NVFP4 |
| Decision training | Rank-16 LoRA plus a ~1M-parameter pointer head on 21 public short-task datasets plus multi-step and generated data | None (zero-shot, policy templates) |
| Readout | Pointer head; each question scored independently over a shared state prefix | Letter readout per slot; all questions read jointly on one canvas |
| Option limit | 255 | 26 natively; more through `dgem systemone serve` bracket routing |
| Calibration as served | Temperature per question type, fitted on its own held-out short tasks | Raw restricted-softmax probabilities |
| Hardware here | Cloud Run, 1× RTX PRO 6000 | Vertex AI G4, 1× RTX PRO 6000 |

- **Same requests:** both models received the same `/v1/systemone` bodies.
- **Same scoring:** one scorer recomputes every metric from the returned distributions. We never use the servers'
  `confidence` fields.
- **Runs:** core suites ran 3 times per model, in parallel. The frozen sets ran once on Strands (it is deterministic)
  and twice on dgem.
- **Latency client:** in the same region, with keep-alive HTTPS.

**Preflight finding.** The stock `strands-decider serve` returned different answers under concurrent requests: one
item moved by 0.82 probability, while serial runs were identical. All Strands results therefore come from the stock
server plus a lock around the engine's `evaluate()`; the lock changes no numerics. This is why the process now
starts with `scripts/compare/preflight.py`.

| Suite | n | Strands' exposure ([`data/sources.md`](https://github.com/strands-labs/strands-decider/blob/main/data/sources.md)) |
|---|---|---|
| JevBench public | 231 | not trained on (Strands ranks itself on it) |
| calibration suite | 50 | 7 of 15 subsets trained on, 4 near |
| intents (banking77, clinc150 slices) | 60 | trained (train split; our items are test rows) |
| tool-call gate (new, ours; author-labelled) | 51 × 2 | unseen |
| typed-decisions test | 2,000 decisions | unseen |
| MASSIVE test, 51 languages | 5,100 | English is its calibration set; others near |
| XNLI test, 15 languages | 4,500 | near (MNLI trained) |
| option order | 739 × 4 orderings | emotion and MASSIVE-en are its calibration sets |

## 4. Calibration

Pool A = JevBench + calibration suite + intents ≤ 26, run 1, n = 341. Held-out = 5-fold temperature fitted out of
sample.

| | Strands v19 | dgem |
|---|---|---|
| ECE10 as served | **0.037** | 0.069 |
| ECE10, held-out global temperature | 0.031 (T ≈ 1.05) | **0.028** (T ≈ 1.5) |
| Brier (multiclass) | 0.333 | **0.215** |
| AUROC (confidence vs correct) | 0.787 | **0.852** |
| Answers at ≥ 0.9 / accuracy there | 31% / 96.3% | **79% / 94.8%** |
| Accuracy at 80% coverage | 82.8% | **94.5%** |

Out of domain, the two fail in opposite directions:

| Suite | Strands: ECE / AUROC / share at ≥ 0.9 | dgem: ECE / AUROC / share at ≥ 0.9 (accuracy there) |
|---|---|---|
| typed-decisions | 0.096 / 0.626 / 3% | 0.180 / **0.771** / 69% (82.6%) |
| MASSIVE | 0.142 / 0.871 / 55% | **0.101 / 0.914** / 81% (92.8%) |
| XNLI | **0.035 / 0.685** / 0.1% | 0.227 / 0.616 / 78% (74.2%) |

- dgem wants T ≈ 1.5 overall and a larger temperature for yes/no questions (1.6–1.9 in pool A, about 3 with the gate
  suite included).
- Strands' shipped temperatures transfer well to JevBench. A per-bucket refit still helps it on long option lists
  (T ≈ 1.5) and score items (T = 0.5).

## 5. The tool-call gate and dgem's cross-slot coupling

The gate suite generalizes Strands' agent example (`examples/strands/tool_call_intervention.py`) to 51 authored
cases, using their exact question wording, true/false criteria and state rendering. There are three kinds of case:

| Kind | Meaning | args_grounded | premature |
|---|---|---|---|
| G | grounded and ready to call | yes | no |
| U | the tool argument was guessed | no | yes |
| A | grounded, but something is left to confirm | yes | yes |

| Mean correct of 3 runs | Strands | dgem |
|---|---|---|
| args_grounded G (21) / U (23) / A (7) | 20 / 23 / 3 | 10.3 / 23 / 3.7 |
| premature G (21) / U (23) / A (7) | 14 / 22 / 6 | 21 / 1.0 / 0.7 |
| both answers the same label (gold 7 of 51) | 11 | 34–40 |

Post-hoc diagnostics (one run each, designed after the result):

| Variant | dgem correct of 102 | dgem: same label in both answers |
|---|---|---|
| both questions in one request | 59 | 36 |
| one question per request | **100** | 5 |
| both in one request, no true/false criteria | 68 | 31 |
| `dgem systemone serve --noul-mode choice` | **95** | 10 |

- On typed-decisions (200 yes/no pairs in one request), dgem's rate of matching answers equals gold (138 vs 139). The
  defect needs related wording with opposite answers.
- Strands is immune by construction: each question is evaluated independently. The flip side is that it cannot use a
  real dependency between questions.

## 6. Latency, throughput and cold start

Measured from a Cloud Run job in the same region, 100 requests per mode.

| Input | Strands server / wall p50 (ms) | dgem server / wall p50 (ms) |
|---|---|---|
| ~200 tokens, 1 question | **34 / 44** | 54 / 62 |
| ~1,000 tokens | **42 / 57** | 57 / 68 |
| ~2,000 tokens | 65 / 80 | **58 / 69** |
| ~3,800 tokens | 118 / 132 | **62 / 74** |
| ~500-token state, 1 / 5 / 10 / 20 yes/no questions | 35 / 72 / 73 / 88 | 55 / 56 / 58 / 59 |

| Throughput (≥ 256 requests per cell) | Strands | dgem |
|---|---|---|
| 1 question, 1 / 16 / 32 workers | 22.6 / 27.3 / 27.4 req/s | 16.1 / 83.9 / 83.5 req/s |
| 5 questions, peak | 66 decisions/s | 321 decisions/s |
| cold start on Cloud Run | 38 s (21 s of it in the first request, which looks like kernel compilation) | none on the dedicated endpoint; about 2.5 min on Cloud Run |

- Strands' time grows linearly with input length. A request with more than one question pays a second forward pass,
  after which extra questions are nearly free.
- dgem's time is dominated by fixed denoising steps.
- Strands' stock server serves one request at a time; dgem batches inside vLLM.
- On the same GPU, dgem's cost per decision at saturation is 3–5× lower. Strands can also run on much cheaper hardware
  (CPU, Mac), which was not measured here.
- **Measurement note.** A first latency pass caught transient load on the shared dgem endpoint (about 100–120 ms on
  five modes). Those modes were repeated, and both passes are in the study receipts.

## 7. Caveats

- **Size class.** 1.9B dense vs 26B-A4B MoE: this is not a same-size comparison. The in-domain parity shows what
  fine-tuning buys a small model; the out-of-domain gap shows what a large zero-shot base buys.
- **Hardware.** Strands targets RTX 3090, Mac and CPU deployments. Both models here ran on an RTX PRO 6000.
- **The gate suite is ours:** n = 51, labelled by the author, not independently reviewed. The coupling finding rests
  on the diagnostics, not on the headline count.
- **dgem nondeterminism** (6.4% of answers change between identical requests) means single dgem runs carry about
  ±3 items of noise on JevBench.

- The server's results under concurrent requests (and a lock as the minimal fix).

## 9. Reproduce

```bash
scripts/compare/preflight.py --competitor strands=<STRANDS_URL>#profile=strands-decider-2b
scripts/bench_matrix.py --matrix benchmarks/matrix/matrix_v2.json run --tier TC \
  --target dgem=<VERTEX_INVOKE_BASE> --baseline dgem \
  --competitor strands=<STRANDS_URL>#profile=strands-decider-2b --competitor-workers 1 --label compare-strands
scripts/compare/report.py benchmarks/runs/<date>-compare-strands
```

The receipts in `benchmarks/runs/20261003-compare-strands-v19` were produced by the study harness that tier TC
replaces, then exported into matrix format. A confirming TC run is queued in the
[register](/dgem/experiments/proposed/#queued-re-runs).
